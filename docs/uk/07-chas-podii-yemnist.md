# 7. Час, події, ємність

Три інструменти, що закривають типові потреби симуляції: керована швидкість
часу, реакція на появу й зникнення сутностей, і зростання світу під непередбачуване
населення.

---

## 7.1. `SimulationClock` — фіксований крок і масштаб часу

### Проблема

Передавати сирий `delta` кадру прямо в симуляцію можна лише доти, доки цей delta
малий. Щойно гравець отримує можливість **прискорити час**, усе ламається: при
масштабі 50× кадр у 16 мс перетворюється на крок у 800 мс.

І тоді все, що просувається по порогу, **перестрибує** через кілька порогів за
одне оновлення:

- клітина, що ділиться у віці 10, за один крок проживає вік 0 → 12 і ділиться
  один раз замість двох;
- снаряд «телепортується» крізь ціль, бо точкова перевірка влучання не бачить
  проміжних позицій;
- кулдаун у 0.2 с спрацьовує один раз замість чотирьох.

Симуляція не просто йде швидше — вона **дає інший результат**. І на повільнішій
машині інший ще раз, бо там delta більший.

### Розв'язок

`SimulationClock` накопичує реальний час, множить його на масштаб і повідомляє,
скільки **однакових** відрізків фіксованого розміру в ньому вміщується.

```gdscript
var clock := SimulationClock.new()
clock.fixed_step = 1.0 / 60.0     # довжина одного відрізка симуляції
clock.time_scale = 4.0            # прискорення
clock.max_substeps = 8            # запобіжник
```

### Використання з фазами (рекомендовано)

```gdscript
func _process(delta: float) -> void:
    var steps: int = clock.advance(delta)

    scheduler.begin_frame()
    for i in steps:
        scheduler.execute_phase(PHASE_SIMULATION, clock.fixed_step)
    # Презентація — рівно один раз на кадр, з РЕАЛЬНИМ delta.
    scheduler.execute_phase(PHASE_PRESENTATION, delta)
```

**Зверніть увагу на два різні delta.** Симуляція отримує `fixed_step`, презентація
— реальний час кадру. Проганяти весь конвеєр через цикл суб-кроків означало б
робити роботу рендера N разів на кадр без жодної користі.

Коли `steps == 0` (пауза, або накопичилося менше за один відрізок), фаза
презентації все одно виконується — саме це тримає гру намальованою.

### Використання без фаз

```gdscript
var steps: int = clock.advance(delta)
if steps == 0:
    scheduler.execute_all(0.0)          # тільки системи без requires_time
else:
    for i in steps:
        scheduler.execute_all(clock.fixed_step)
```

### Запобіжник від «спіралі смерті»

`max_substeps` — не просто обмеження. Це захист від відомої патології: якщо один
кадр був повільним, в акумуляторі накопичилося більше часу; проганяти все
накопичене зробить кадр іще повільнішим, що накопичить іще більше — і гра
зависає назавжди.

Понад `max_substeps` надлишок **відкидається**: симуляція ненадовго йде в
сповільненому темпі замість того, щоб заблокуватися.

```gdscript
clock.dropped_substeps     # скільки відрізків відкинуто всього
clock.is_saturated()       # чи впирається просто зараз
```

Постійно зростаючий `dropped_substeps` означає, що машина не тягне запитаний
`time_scale`. Це чесний сигнал, а не помилка.

### Інтерполяція

Якщо частота симуляції нижча за частоту кадрів, рух виглядає ступінчастим.
`get_alpha()` повертає частку невитраченого відрізка в `[0, 1)`:

```gdscript
var alpha: float = clock.get_alpha()
var drawn_position: Vector3 = previous_position.lerp(current_position, alpha)
```

### Повний API

```gdscript
clock.advance(real_delta) -> int    # викликати РІВНО раз на кадр
clock.fixed_step                    # довжина відрізка
clock.time_scale                    # 0 = стоп, 1 = реальний час, 50 = швидко
clock.max_substeps                  # запобіжник
clock.paused                        # заморозити, не втрачаючи акумулятор
clock.get_last_substeps()
clock.get_alpha()
clock.is_saturated()
clock.get_effective_time_scale(real_delta)   # фактична швидкість проти запитаної
clock.elapsed_simulated             # точна сума, без дрейфу
clock.total_substeps
clock.dropped_substeps
clock.reset()                       # на перезапуску рівня
```

> `elapsed_simulated` зростає рівно на `fixed_step` за відрізок, тому він
> **точний**, на відміну від суми дробових delta, яка накопичує похибку.

## 7.2. Журнал змін — реакція на появу і смерть

Бібліотека навмисно не має подій «компонент додано / видалено»: сигнали в
гарячому циклі на десятках тисяч сутностей коштували б дорожче за саму роботу.

Натомість є **журнал структурних змін**, який вмикається на конкретному сховищі.

```gdscript
enemies.track_changes = true
```

Доки прапорець вимкнений (типово), він коштує **одну перевірку на структурну
операцію**, тобто фактично нічого.

### Читання журналу

```gdscript
class DeathEffectSystem extends EcsSystem:
    var _context: Context

    func _init() -> void:
        system_name = "DeathEffects"

    func setup(_world: EcsWorld, context) -> void:
        _context = context

    func execute(_delta: float) -> void:
        var enemies: EnemyStore = _context.enemies

        for i in enemies.added_count:
            var entity: int = enemies.added_entities[i]
            _spawn_appear_effect(entity)

        for i in enemies.removed_count:
            var entity: int = enemies.removed_entities[i]
            _spawn_death_effect(entity)

        _context.world.clear_change_logs()
```

### Куди ставити систему-читача

**Одразу після `EcsReaperSystem`.** На цей момент:

- `added_entities` містить усе, що з'явилося цього кадру;
- `removed_entities` містить усе, що загинуло цього кадру (жнець уже відпрацював).

```gdscript
scheduler.add_system(SpawnSystem.new())
scheduler.add_system(CombatSystem.new())
scheduler.add_system(EcsReaperSystem.new(world))
scheduler.add_system(DeathEffectSystem.new())     # ← читає журнал і чистить його
```

### Правила

- Дійсні префікси — `[0, added_count)` і `[0, removed_count)`. Розмір самих
  масивів більший, решта — сміття.
- **Порядок не визначений.** Не спирайтеся на нього.
- Сутність, створена й знищена в одному кадрі, потрапить в **обидва** журнали.
  Це коректно.
- `clear()` і `world.reset()` **не пишуть** окремі видалення — вони піднімають
  прапорець `change_log_overflowed`. Проганяти всю популяцію через журнал при
  перезапуску рівня — не те, чого хоче викликальний код.
- `world.clear_change_logs()` чистить журнали всіх сховищ, у яких вони увімкнені.

### Вартість

Увімкнення виділяє два буфери, які ростуть подвоєнням, доки не досягнуть розміру
типової кадрової плинності. Далі — стала пам'ять і по одному запису в масив на
структурну операцію.

## 7.3. Ємність і політика зростання

### Явне зростання

```gdscript
if world.reserve_capacity(200_000):
    _resize_my_render_buffers(200_000)
```

Світ і **усі** зареєстровані сховища ростуть разом; наявні сирі id, handle і
щільні слоти лишаються дійсними.

Це **алокуючий бар'єр**. Викликайте його на екрані завантаження або на явній
межі фаз — ніколи посеред обходу систем.

Якщо хоча б одне сховище не підтримує зростання (не має `_grow_dense`), метод
поверне `false`, **не змінивши нічого**. `EcsPackedStore` і `EcsTagStore`
підтримують його завжди.

> Бібліотека може збільшити лише **власні** буфери. Все, що ваша гра виділила
> паралельно — `MultiMesh`, батчі фізики, мережеві масиви — ваша відповідальність.

### Автоматична політика

Для симуляції з вибуховим ростом населення — поділ клітин, ланцюгова реакція,
хвилі — чекати на `create_entity() == -1` пізно: спавни вже почали губитися.

```gdscript
var policy := EcsCapacityPolicySystem.new(world)
policy.grow_threshold = 0.8          # рости при 80% заповнення
policy.growth_factor = 1.5           # нова ємність = стара × 1.5
policy.maximum_capacity = 500_000    # стеля; 0 = без обмеження
policy.check_interval_frames = 30
policy.on_capacity_grown = _on_world_grown

scheduler.add_system(EcsReaperSystem.new(world))
scheduler.add_system(policy)          # ← ОДРАЗУ після жнеця
```

```gdscript
func _on_world_grown(previous: int, next: int) -> void:
    _render_buffer.resize(next)
    print("світ виріс: %d → %d" % [previous, next])
```

**Реєструйте одразу після жнеця** або на іншій явній межі фаз: зростання
переалокує всі буфери, тому жодна система не має тримати щільний слот чи
псевдонім масиву через цей виклик.

Примусова перевірка, якщо ви наперед знаєте про майбутній сплеск:

```gdscript
policy.grow_now()
```

Діагностика: `policy.growth_count`, `policy.last_growth_capacity`.

### Скільки ємності брати одразу

Пам'ять на сутність — це приблизно:

- **світ:** ~23 байти на сутність службових даних;
- **кожне сховище:** 8 байт (sparse + dense) плюс розмір payload.

Для 100 000 сутностей і 10 сховищ по 16 байт payload це близько
`100k × (23 + 10 × 24) ≈ 26 МБ`. Виділити наперед більше, ніж треба, майже
завжди дешевше, ніж рости під час гри.

## Головне з розділу

1. `SimulationClock` робить симуляцію **відтворюваною** при будь-якій швидкості
   часу; сирий delta цього не дає.
2. Симуляція отримує `fixed_step`, презентація — реальний `delta`.
3. `max_substeps` — запобіжник від спіралі смерті; відкинуті відрізки видно.
4. Журнал змін (`track_changes`) — це «події появи й смерті»; читач ставиться
   одразу після жнеця й сам чистить журнал.
5. `reserve_capacity()` — алокуючий бар'єр; лише на безпечній межі.
6. `EcsCapacityPolicySystem` росте **заздалегідь**, а не після втрати спавнів.
