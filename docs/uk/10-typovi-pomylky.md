# 10. Типові помилки

Довідник у форматі «симптом → причина → виправлення». Більшість цих помилок
**не дають повідомлень у консолі** — саме тому цей розділ існує.

---

## 10.1. Тихі помилки (найнебезпечніші)

### Після видалення дані перемішалися

**Симптом.** Сутності живі, компоненти на місці, але значення належать не тим —
у ворога чуже здоров'я, снаряд летить не туди. Помилок немає.

**Причина.** Ручне сховище (`EcsComponentStore`) не реалізувало
`_relocate_dense()`. При swap-remove на місце видаленого приїхав останній
елемент, але його payload лишився на старому місці.

**Виправлення.**

```gdscript
func _relocate_dense(from_slot: int, to_slot: int) -> void:
    # КОЖНЕ поле, без винятку
    health[to_slot] = health[from_slot]
    armor[to_slot] = armor[from_slot]
```

**Як не наступити знову.** Використовуйте `EcsPackedStore` — там це реалізовано
за вас, і забути неможливо. Якщо сховище має бути ручним, напишіть на нього
окремий тест: створіть дві сутності з **розрізнюваними** значеннями всіх полів,
видаліть першу, перевірте другу.

---

### Дані пишуться, але не зберігаються

**Симптом.** Система щось записує, наступна система цього не бачить.

**Причина.** Найчастіше — індексація масиву даних **ідентифікатором сутності**
замість щільного слота.

```gdscript
# НЕПРАВИЛЬНО
positions.x[entity] = 5.0

# ПРАВИЛЬНО
var slot: int = positions.index_of(entity)
if slot != -1:
    positions.x[slot] = 5.0
```

**Рідший варіант:** ви присвоїли полю сховища цілком новий масив
(`store.x = PackedFloat32Array()`), і в `EcsPackedStore` кеш посилань застарів.
Викличте `store.refresh_tracked_arrays()` — або, краще, не присвоюйте поля
цілком.

---

### Система читає дані минулого кадру

**Симптом.** Зіткнення спрацьовують із запізненням, наведення «відстає» на кадр,
індекс сусідів показує старі позиції.

**Причина.** Система стоїть **не на своєму місці** у списку реєстрації.

```gdscript
# НЕПРАВИЛЬНО: індекс будується за старими позиціями
scheduler.add_system(SpatialIndexSystem.new())
scheduler.add_system(MovementSystem.new())

# ПРАВИЛЬНО
scheduler.add_system(MovementSystem.new())
scheduler.add_system(SpatialIndexSystem.new())
```

**Порядок реєстрації — це поведінка.** Помилки не буде; буде інша гра.

---

### Use-after-free всередині кадру

**Симптом.** Зрідка, «раз на сто кадрів», дані належать не тій сутності.

**Причина.** Щільний слот закешовано **через** структурну зміну.

```gdscript
# НЕПРАВИЛЬНО
var slot: int = positions.index_of(entity)
world.flush_destroy_queue()          # swap-remove міг перемістити дані
positions.x[slot] = 0.0              # пишемо в чужий компонент
```

**Виправлення.** Брати слот заново після будь-якої структурної зміни. І тримати
`flush_destroy_queue()` **рівно в одній точці кадру** — використовуйте
`EcsReaperSystem`.

> Handle лікує протухле **посилання на сутність**, але не протухлий **слот**.

---

### Обхід розсипався на ходу

**Симптом.** Частина сутностей пропускається, лічильники не сходяться.

**Причина.** Склад сховища змінюється **посеред обходу цього ж сховища**.

```gdscript
# НЕПРАВИЛЬНО
for dense in positions.count:
    if should_die(dense):
        positions.detach(positions.dense_entities[dense])   # масив зсунувся
```

**Виправлення.** Позначити, а прибрати пізніше:

```gdscript
for dense in positions.count:
    if should_die(dense):
        world.queue_destroy(positions.dense_entities[dense])
```

## 10.2. Помилки з повідомленням у консолі

### `create_entity()` повернув -1

**Причина.** Світ заповнений: `get_free_count() == 0`.

**Виправлення.** Або збільшити початкову ємність, або
[`EcsCapacityPolicySystem`](07-chas-podii-yemnist.md#73-ємність-і-політика-зростання),
або знищувати активніше. І **завжди перевіряйте результат** — це не виняткова
ситуація, а нормальний стан.

---

### `register_store()` повернув `false`

Три можливі причини:

| Повідомлення | Причина |
|---|---|
| `schema locked by the first create_entity()` | Сховище реєструється **після** першої сутності. Реєструйте всі сховища до створення. |
| `component type N already registered` | Продубльована константа типу. |
| `store already registered under another type id or world` | Той самий об'єкт сховища вставляють двічі. |

---

### `reserve_capacity()` повернув `false`

**Причина.** Або запитано менше за поточну ємність, або якесь сховище не має
`_grow_dense()`.

**Виправлення.** Додайте хук у ручне сховище:

```gdscript
func _grow_dense(_previous_capacity: int, dense_capacity: int) -> void:
    values.resize(dense_capacity)
```

`EcsPackedStore` і `EcsTagStore` підтримують зростання завжди. Перевірити:
`store.supports_capacity_growth()`.

---

### `_clear_relocated_dense() without _release_dense()`

**Причина.** Ви реалізували очищення дубліката, але не звільнення того, що
видаляється. Це майже завжди означає **витік ресурсу**.

**Виправлення.** Реалізуйте обидва — див.
[розділ 4.6](04-komponenty-i-skhovyshcha.md#46-компоненти-з-володінням-ресурсами).

---

### `one instance cannot be registered in two schedulers`

**Причина.** Один об'єкт `EcsSystem` додано в два планувальники.

**Виправлення.** Створіть окремий екземпляр для кожного конвеєра.

---

### `system X did not declare access to type N`

**Причина.** Діагностика `view.validate_owner_access()`: система використовує
через View тип, якого не оголосила.

**Виправлення.** Або допишіть `declare_read/declare_write`, або не викликайте
валідацію. На виконання це не впливає ніяк.

---

## 10.3. Проблеми продуктивності

### Кадр «просідає» рівно тоді, коли багато хто гине

**Причина.** Знищення коштує `O(жертви × сховища)`.

**Виправлення.**
- Об'єднайте дрібні сховища.
- Розтягніть масову смерть на кілька кадрів.
- Для повного очищення беріть `world.reset()`, а не масове `queue_destroy`.

---

### Перебудова сітки з'їдає весь кадр

**Причина.** Невдалий `cell_size`: вартість — `O(записи + КОМІРКИ)`.

**Виправлення.** `UniformSpatialGrid.suggest_cell_size()`, плоский режим для гри
на площині, окремі сітки для наборів з різним населенням. Див.
[розділ 8.4](08-prostorovyi-poshuk.md#84-найважливіше-підбір-cell_size).

---

### `EcsQuery` перебудовується щокадру

**Причина.** Якесь сховище-учасник щокадру змінює склад — часто це тег, який
хтось причіпляє й віддирає кожен кадр.

**Перевірка:**

```gdscript
print(query.get_rebuild_count())     # росте на 1 щокадру?
```

**Виправлення.** Або приберіть мінливий тег зі складу запиту, або перейдіть на
`EcsView` / прямий цикл — кеш, що промахується завжди, тільки додає роботи.

---

### Обхід повільніший, ніж очікувалося

**Причина.** Читання полів об'єкта в циклі замість локальних псевдонімів.

**Виправлення.** Див.
[розділ 9.1](09-produktyvnist.md#91-модель-вартості-gdscript).

## 10.4. Помилки при прискоренні часу

### Симуляція «перестрибує» події на високій швидкості

**Симптом.** При `time_scale = 50` клітини діляться рідше, ніж мали б; снаряди
пролітають крізь цілі.

**Причина.** Сирий `delta`, помножений на масштаб, дає величезний крок.

**Виправлення.** [`SimulationClock`](07-chas-podii-yemnist.md#71-simulationclock--фіксований-крок-і-масштаб-часу).

---

### Гра зависає при прискоренні

**Причина.** «Спіраль смерті»: кожен наступний кадр повільніший за попередній.

**Виправлення.** `clock.max_substeps` (типово 8). Перевіряйте
`clock.dropped_substeps` — якщо зростає, машина не тягне запитану швидкість.

---

### На паузі щось усе одно рухається

**Причина.** Система не оголосила `requires_time = true`.

**Виправлення.**

```gdscript
func _init() -> void:
    system_name = "Movement"
    requires_time = true
```

---

### Сутності накопичуються в черзі під час паузи

**Причина.** Жнець отримав `requires_time = true`.

**Виправлення.** Не робіть цього. `EcsReaperSystem` навмисно працює й на паузі.

---

## 10.5. Швидка діагностика

Коли незрозуміло, що взагалі відбувається:

```gdscript
# 1. Чи цілий світ?
if not world.validate_integrity():
    breakpoint

# 2. Що з населенням?
print("live=%d free=%d pending=%d load=%.2f" % [
    world.get_live_count(), world.get_free_count(),
    world.get_pending_destroy_count(), world.get_load_factor()])

# 3. Чи узгоджені сховища зі світом?
print("positions=%d hostiles=%d" % [positions.count, hostile_tag.count])

# 4. Куди йде час?
for i in scheduler.get_system_count():
    print("%-24s %6d мкс" % [scheduler.get_system_name(i),
        int(scheduler.get_average_timing_usec(i))])

# 5. Чи правильно зібраний конвеєр?
scheduler.validate_pipeline(world)
```

## Чекліст перед тим, як шукати баг деінде

- [ ] Ручні сховища реалізують `_relocate_dense()` для **кожного** поля?
- [ ] `flush_destroy_queue()` викликається **рівно в одному місці**?
- [ ] Дані індексуються **слотом**, а не id сутності?
- [ ] Порядок систем відповідає порядку залежностей за даними?
- [ ] Щільні слоти не кешуються через структурні зміни?
- [ ] Склад сховища не змінюється посеред обходу?
- [ ] `create_entity()` перевіряється на -1?
- [ ] Системи, залежні від часу, мають `requires_time = true`?
