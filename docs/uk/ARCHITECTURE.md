# Архітектура Aegis ECS

Цей документ описує розширену модель Aegis для великої гри. Головний принцип не
змінився: найшвидший шлях залишається простим циклом по щільних `Packed*Array`.
Безпека й універсальність додані окремими cold-path API, тому частинка чи снаряд
не платить за функції, якими не користується.

Це **довідник рішень**, а не підручник. Якщо ви шукаєте пояснення «як цим
користуватися» — почніть з [посібника](README.md).

## Шари

```text
EcsWorld
  ├─ розподільник сирих id + відкладена черга знищення
  ├─ пакетні create_entities() / queue_destroy_many()
  ├─ покоління + тег світу → безпечний міжкадровий handle
  ├─ реєстр sparse-множин EcsComponentStore
  └─ явні бар'єри ємності та перевірки цілісності

Сховища
  EcsComponentStore        sparse set, автовизначення необов'язкових хуків
    ├─ EcsPackedStore      декларативне: track() полів — і більше нічого
    └─ EcsTagStore         без payload, спеціалізоване пакетне видалення

Обхід
  ├─ прямий sparse loop    найшвидший, з'єднання руками
  ├─ EcsView               живий фільтр без алокацій
  └─ EcsQuery              преалокований кеш складу

Виконання
  EcsScheduler
    ├─ порядок реєстрації — це поведінка
    ├─ вимикачі систем/фаз, пропуск за requires_time
    ├─ метадані читання/запису й аналіз конфліктів
    └─ профілювання (накопичення за кадр + згладжене середнє)

Готові системи
  ├─ EcsReaperSystem            єдина точка знищення
  └─ EcsCapacityPolicySystem    росте раніше, ніж світ заповниться

Допоміжне
  ├─ SimulationClock        фіксований крок, масштаб часу, запобіжник
  ├─ UniformSpatialGrid     broadphase на counting sort, плоский 2D-режим
  └─ AngleMath              доворот кута найкоротшим шляхом
```

## Сирий id і generational handle

Сирий id — індекс від `0` до `capacity - 1`. Він напряму адресує `sparse_index`,
тому лишається найдешевшим представленням у гарячому циклі.

Сирий id не можна вважати стабільним посиланням через structural sync point.
Після знищення той самий індекс може отримати інша сутність. Для цілі, власника,
виділення в UI, tween, сигналу, async-колбека та зовнішньої черги
використовується додатний 63-бітовий handle:

```text
біти  0..23  сирий id сутності  (до 16 777 216 слотів)
біти 24..47  покоління          (до 16 777 215 життів слота)
біти 48..62  тег світу в процесі
біт      63  0
```

```gdscript
var entity: int = world.create_entity()
var handle: int = world.make_handle(entity)

# Через багато кадрів:
entity = world.entity_from_handle(handle)
if entity == EcsWorld.INVALID_ENTITY:
	return
```

Handle відхиляється, якщо не збігся тег світу, покоління, діапазон або стан
«живий». При переповненні покоління слот стає `retired` і більше не видається:
старий handle не оживе навіть теоретично. Теги світів не перевикористовуються;
після 32 767 створених світів у одному процесі нові світи працюють із сирими id,
але handle-API повідомляє помилку.

Runtime handle **не є** save/network ID. Між запусками використовуйте власний
GUID або доменний стабільний ключ.

## Життєвий цикл і структурні епохи

```text
FREE → ALIVE → PENDING_DESTROY → FREE
                              ↘ RETIRED при переповненні покоління
```

`queue_destroy*()` не змінює сховищ. Позначена сутність і її handle лишаються
дійсними до `flush_destroy_queue()`. Flush є structural sync point:

1. повторно перевіряє generation-stamped ключ із черги;
2. від'єднує сутність від кожного сховища;
3. виконує swap-remove і хуки очищення;
4. позначає сутність мертвою;
5. збільшує покоління;
6. і лише тоді повертає сирий id у стек вільних.

Flush можна мати на кількох межах фаз. Не можна виконувати його посеред системи
або зберігати щільний слот через цю межу. Generational handle лікує протухле
посилання на сутність, але не протухлий щільний слот.

`reset()` інвалідує handle всіх активних і позначених сутностей, очищає сховища
й чергу, але зберігає реєстрації та ємність. Схема блокується першим успішним
`create_entity()`; усі сховища мають реєструватися заздалегідь.

## Сховища й очищення посилань

Сховище — sparse set із двонаправленим відображенням:

```text
sparse_index[entity] → щільний слот або -1
dense_entities[slot] → сутність
payload[slot]        → дані компонента
```

Спадкоємець завжди реалізує `_reserve_dense()` і `_relocate_dense()`. Якщо
payload містить посилання, додаються хуки:

```gdscript
func _release_dense(slot: int) -> void:
	owner_api.release(resources[slot]) # потрібний API для owned RID/native handle
	resources[slot] = null

func _clear_relocated_dense(slot: int) -> void:
	resources[slot] = null # володіння вже перенесено; повторно не звільняємо

func _clear_dense(active_count: int) -> void:
	for slot in active_count:
		# звільнити володіння кожного активного payload
		resources[slot] = null
```

Detach спершу викликає `_release_dense(removed_slot)`, потім переносить останній
payload і викликає `_clear_relocated_dense(last_slot)`. Змішувати ці операції не
можна: інакше видалений RID витече, а перенесений може бути звільнений двічі.
Без хуків преалокований масив продовжить утримувати видалені `Resource`, `RID`,
`Callable` або `Object`.

`structural_version` змінюється при новому attach, успішному detach, непорожньому
clear і зростанні ємності. Запис payload version не змінює: склад запиту
лишається тим самим.

## Вибір між прямим циклом, View і Query

### Прямий цикл

Використовуйте в найгарячіших системах із відомою схемою. Ведучим обирається
найменше сховище, решта компонентів перевіряється через sparse-масиви.

```gdscript
var entities := velocities.dense_entities
var position_slots := positions.sparse_index
for velocity_slot in velocities.count:
	var entity: int = entities[velocity_slot]
	var position_slot: int = position_slots[entity]
	if position_slot == -1:
		continue
```

### EcsView

`EcsView` розв'язує required/excluded type ID один раз. `refresh_driver()`
обирає найменше обов'язкове сховище, `matches()` читає актуальні sparse-множини.
Після `configure()` steady-state API не будує масив результату й не алокує.

View зручніший за ручне з'єднання, але `matches()` лишається викликом методу на
кандидата. Для найгарячіших систем беріть із View самі sparse-масиви
(`get_required_sparse()`) і вбудовуйте перевірку у власний цикл.

### EcsQuery

`EcsQuery` матеріалізує id сутностей у заздалегідь виділений буфер. Типово його
розмір дорівнює `world.capacity`; необов'язковий `maximum_results` обмежує буфер
для запиту з відомою верхньою межею. Query стежить за `structural_version` і
пропускає перебудову, якщо склад не змінювався.

```gdscript
if query.refresh():
	# склад справді змінився
for index in query.count:
	var entity: int = query.entity_at(index)
```

Перебудова піднімає всі sparse-масиви учасників у локальні змінні й
спеціалізує найчастіші арності (1 обов'язковий, 1 виключений, тощо), тому не
викликає `matches()` зовсім. Це дало 5.4x проти реалізації 1.1.

При обмеженому буфері `count` ніколи не перевищує `maximum_results`, а
`is_truncated()` повідомляє, що відповідних сутностей було більше. Без ліміту
пам'ять результату — приблизно 4 байти × `world.capacity` на кожен Query:
100 повних запитів при ємності 1 000 000 зайняли б близько 381 МіБ.

`get_entities_unsafe()` прибирає виклик методу, але буфер вважається read-only, а
псевдонім не можна зберігати через `refresh()` чи `reserve_capacity()`.

View/Query вимагають щонайменше один обов'язковий тип: світ навмисно не тримає
другого щільного списку «всіх живих» лише заради запиту без компонентів.

## Планувальник, фази й метадані

Планувальник ніколи не сортує системи. Порядок реєстрації лишається повною
специфікацією поведінки. Фаза — фільтр і метадані:

```gdscript
scheduler.add_system(InputSystem.new(), 100)
scheduler.add_system(MovementSystem.new(), 200)
scheduler.add_system(RenderUploadSystem.new(), 300)
scheduler.add_system(EcsReaperSystem.new(world), 400)
```

Звичайний кадр використовує `execute_all(delta)`. Якщо фази викликаються з різних
місць, один раз закрийте попередній кадр:

```gdscript
scheduler.begin_frame()
scheduler.execute_phase(100, delta)
scheduler.execute_phase(200, delta)
scheduler.execute_phase(300, delta)
scheduler.execute_phase(400, delta)
```

Заміри **накопичуються** між двома `begin_frame()`, тому кадр із фіксованим
кроком, що виконує фазу симуляції чотири рази, звітує сумарну вартість цих
чотирьох суб-кроків — тобто те, що реально потрапило в бюджет кадру. Згладжене
середнє згортається один раз на кадр, а не на кожен суб-крок.

`enabled` і перемикання фаз не видаляють системи, тому індекси профайлера
стабільні. Вимкнена система отримує timing `0` і `was_system_executed() == false`.

### Пропуск за `requires_time`

Пауза — це нульовий крок, а не пропущений кадр. Історично кожна залежна від часу
система мусила починатися з `if delta <= 0.0: return`, і забути цей рядок було
тихим багом. Тепер система оголошує `requires_time = true` в `_init()`, і
планувальник пропускає виклик повністю — це і безпечніше, і трохи швидше.

`EcsReaperSystem` навмисно має `requires_time = false`: сутності, позначені на
знищення перед паузою, мають бути прибрані, інакше вони висять у черзі й у всіх
сховищах увесь час паузи.

### Метадані доступу

Задаються в `_init()`:

```gdscript
declare_read(TYPE_INPUT)
declare_write(TYPE_POSITION)
declare_structural_write(TYPE_SLEEPING)
writes_world_structure = true  # create/destroy/reset
complete_access_metadata()
```

Метадані не змінюють порядок і не створюють runtime-перевірок. Вони
використовуються для `validate_pipeline()`, перевірки власника View/Query і
`systems_conflict()`. Останній консервативно відповідає, чи могли б дві системи
увійти в майбутній паралельний батч. Доки система не викликала
`complete_access_metadata()`, її доступ вважається невідомим і конфліктує з
будь-якою іншою — щоб старий код не міг випадково потрапити в небезпечний
паралельний батч. Поточний планувальник лишається послідовним.
`writes_world_structure` завжди конфліктує з усіма системами: create/destroy/reset
змінюють валідність сирих id і всіх View навіть у системи без оголошень.

Після `add_system()` поле `system_phase` заморожене. Runtime-перенесення виконує
`scheduler.set_system_phase(index, phase)`: так enable-стан фази не розходиться з
системою. Один екземпляр системи не можна ділити між двома планувальниками.

`teardown_all()` викликає системи у зворотному порядку — ресурси розбираються як
стек відносно `setup`.

## Зростання ємності

Сталий кадр ніколи не росте автоматично. Якщо прогноз змінився:

```gdscript
# екран завантаження / зупинений конвеєр
world.reserve_capacity(200_000)
```

Світ і всі зареєстровані сховища ростуть разом; наявні сирі id, handle і щільні
слоти зберігаються. Власні зовнішні буфери гри (`MultiMesh`, батчі фізики,
мережеві масиви) бібліотека збільшити не може — це обов'язок коду завантаження.
Query адаптує свій кеш при наступному `refresh()`.

Зростання для власного сховища — opt-in через сам факт визначення хука.
Ініціалізація і зростання розділені, щоб випадковий повторний `_reserve_dense()`
не стер живі дані:

```gdscript
func _grow_dense(_old_capacity: int, new_capacity: int) -> void:
	positions.resize(new_capacity) # зобов'язано зберегти [0, count)
```

Окремого прапорця немає: сховище підтримує зростання тоді й лише тоді, коли
`_grow_dense()` визначено. Перевіряється це один раз, при реєстрації, через
`has_method()` — працює точно, бо базовий клас цей метод навмисно **не оголошує**.
Публічно стан доступний як `store.supports_capacity_growth()`. `EcsPackedStore` і
`EcsTagStore` визначають хук завжди.

Перед зміною масивів світ перевіряє ємність і підтримку зростання в кожного
сховища. Якщо хоча б одне не opt-in, `reserve_capacity()` повертає `false`, не
змінивши ні світ, ні сховища. Прямого публічного зростання окремого сховища
немає: розсинхронізувати його ємність із власником через штатний API не можна.

## Автовизначення необов'язкових хуків

Той самий механізм застосовано до всіх необов'язкових хуків сховища:

```text
_grow_dense               -> дозволяє reserve_capacity()
_relocate_dense_batch     -> вмикає пакетний перенос payload
_release_dense            -> вмикає ownership-шлях detach
_clear_relocated_dense    -> очищення moved-from дубліката
_clear_dense              -> масове очищення при clear()/reset()
```

Базовий клас не оголошує жодного з них, тому `has_method()` дає точну відповідь
«чи визначив спадкоємець». Це усуває цілий клас тихих багів: інакше така
можливість керувалася б булевим прапорцем, який можна виставити неправильно
(забув виставити → ресурс тихо тече; виставив зайвий раз → платиш за
невикористовуваний шлях). Вартість виклику через `call()` у GDScript практично
дорівнює прямому виклику (замір: 94.6 нс проти 91.9 нс), тому за точність
диспетчеризації платити не доводиться.

Ціна пропуску хука реальна: порожній віртуальний виклик коштує ~90 нс проти
~20 нс за читання елемента масиву. На 10 000 сутностей × 4 компоненти це ~7 мс за
кадр, якби хуки викликалися вхолосту.

## Пакетне знищення

`flush_destroy_queue()` — найдорожча структурна операція: знищити одну сутність
означає від'єднати її від **кожного** зареєстрованого сховища. При 12 сховищах і
10 000 сутностей це 120 000 пар.

Реалізація store-major, а не entity-major, і адаптивна:

```text
1. Розв'язати ключі черги й ущільнити тих, що вижили, у той самий масив.
   Він же стає списком жертв — окремого scratch-буфера немає.
2. Для кожного сховища обрати дешевший обхід:
      count <= reaped * 2   -> detach_flagged(flags)  — O(count)
      інакше                -> detach_many(queue, n)  — O(reaped)
3. Завершити lifecycle: alive = 0, generation++, повернути id у стек вільних.
```

**Чому store-major.** Усередині `detach_many()` sparse/dense-масиви живуть у
локальних змінних, тому пара, у якої компонента немає, коштує одне читання
локального масиву замість читання поля об'єкта плюс виклику методу. У типової
сутності є лише частина компонентів, тому домінує саме цей skip-шлях.

**Чому адаптивно.** Сховище на одну сутність (турель, гравець) не має
переглядати 10 000 жертв. Обхід власного щільного масиву з перевіркою байтового
прапорця коштує O(count).

**Чому `detach_flagged()` швидший при масовій смерті.** Знаючи наперед, які
елементи приречені, він не переносить приречений елемент у щойно звільнений слот,
щоб видалити його наступним кроком: спершу відсікаються помічені елементи з
хвоста (їм переміщення не потрібне взагалі), і тільки потім ті, що вижили,
заповнюють дірки. При знищенні всієї популяції переміщень **нуль** замість одного
на видалення.

Поріг `count <= reaped * 2` підібрано так: економія — це `removed × f` переміщень
(f — частка сховища, що потрапила під видалення), зайва робота — `(count - reaped)`
ітерацій. При переміщенні ~200 нс та ітерації ~20 нс перехід відбувається близько
2–3x; взято консервативне 2x.

`detach_many()` (без прапорців) переносити менше не може: список жертв не дає
дешевої відповіді на питання «а хвостовий елемент теж приречений?».

### Пакетний перенос payload

Коли у сховища немає ownership-хуків, ніщо не читає payload по ходу циклу, тому
всі переміщення можна записати й застосувати одним проходом у тому самому
порядку — це еквівалентно чергуванню. Тоді спадкоємець дістає свої масиви один
раз на всю операцію, а не на кожне переміщення:

```gdscript
func _relocate_dense_batch(from_slots, to_slots, move_count) -> void:
	for i in _tracked_arrays.size():
		var array = _tracked_arrays[i]
		for move in move_count:
			array[to_slots[move]] = array[from_slots[move]]
```

Замір: винесення доступу до масиву з внутрішнього циклу дає 43 → 23 нс на
переміщення. Саме тому `EcsPackedStore` не програє рукописному сховищу
(7.58 мс проти 7.55 мс на 10k × 4), попри узагальненість.

Сховище з ownership використовує чергуючий шлях: `_release_dense()` зобов'язаний
відпрацювати **до** того, як payload перезапишуть, тому відкласти перенос не можна.

## Валідація й тестування

`world.validate_integrity()` перевіряє:

- `live + free + retired == capacity`;
- унікальність списку вільних і черги знищення;
- відповідність прапорців і черги;
- стан «живий» у кожної сутності зі сховища;
- бієкцію sparse↔dense і межі слотів;
- однакову ємність світу й сховищ.

Перевірка лінійна і створює тимчасові debug-буфери, тому не має працювати
кожного продакшн-кадру.

```bash
godot --headless --script res://addons/aegis_ecs/tests/test_advanced_ecs.gd
godot --headless --script res://addons/aegis_ecs/tests/test_ecs_features.gd
```

`test_advanced_ecs.gd` покриває ABA-перевірку handle, відхилення чужого світу,
reset/зростання, хуки очищення, кешування View/Query, керування планувальником і
5 000 випадкових структурних операцій.

`test_ecs_features.gd` додатково перевіряє пакетні шляхи **диференційно**: ті самі
видалення проганяються через `detach()` по одному і через `detach_many()` /
`detach_flagged()`, після чого порівнюється підсумкове відображення
entity → payload. Оптимізований шлях зобов'язаний бути невідрізнимим від
наївного, і це єдиний спосіб переконатися в цьому надійно.

`_relocate_dense()` не може бути універсально перевірений для довільного payload.
Кожне користувацьке сховище має мати власний relocation-тест із розрізнюваними
значеннями всіх полів.

## Рекомендована структура великої гри

- Один `EcsWorld` на незалежну симуляцію/матч, не глобальний singleton.
- Type ID — єдиний enum модуля, зареєстрований до першої сутності.
- Гарячі когезивні дані допустимо тримати в одному сховищі; необов'язкові ознаки
  й рідкісні підсистеми виносити в окремі сховища/теги.
- Сирі id не виходять із систем; публічні сервіси, UI і колбеки отримують handle
  або доменні GUID.
- Структурні писачі згруповані у зрозумілі межі фаз.
- Прямі цикли використовуються після профілювання, а не типово всюди.
- `validate_integrity(false)` запускається в CI/fuzz і за командою debug-панелі.
- Шар save/network серіалізує доменну схему, а не внутрішні щільні слоти.
- Сховища тільки з даними успадковують `EcsPackedStore`; рукописний
  `EcsComponentStore` лишається для нестандартної розкладки.
- Знищення — через єдиний `EcsReaperSystem`, зареєстрований останнім;
  `EcsCapacityPolicySystem` одразу за ним.
- Залежні від часу системи оголошують `requires_time = true` замість ручної
  перевірки `delta <= 0.0`.
- Реакція на появу/смерть — через opt-in журнал змін сховища, а не через сигнали:
  читач ставиться одразу після жнеця.
- Керована швидкість часу — через `SimulationClock` із фіксованим кроком; сирий
  `delta × time_scale` розсинхронізовує симуляцію по порогах.

## Свідомі обмеження

Aegis не надає archetype chunks, автоматичного паралельного планувальника,
протоколу rollback/snapshot і універсальної серіалізації. Реактивність є, але у
вигляді явного opt-in журналу структурних змін, а не сигналів: ціна ввімкнення
видима, а вимкнений журнал коштує одну перевірку на структурну операцію.

Нові API дають безпечну основу для великої гри, не перетворюючи компактне
GDScript-ядро на прихований runtime із непередбачуваною вартістю.
