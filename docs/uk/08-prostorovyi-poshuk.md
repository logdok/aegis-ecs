# 8. Просторовий пошук

---

## 8.1. Задача

«Які об'єкти зараз поруч із точкою X?»

Наївна відповідь — перебрати всі й порівняти відстань. Це `O(n)` на один запит.
Якщо запитів теж `n` (кожен ворог шукає найближчого сусіда), виходить `O(n²)`:
на 10 000 об'єктів це 100 мільйонів перевірок за кадр. Неприйнятно вже на кількох
тисячах.

`UniformSpatialGrid` розв'язує це поділом простору на однакові комірки. Об'єкт
потрапляє в комірку за своїми координатами, а пошук «хто поруч» зводиться до
перегляду кількох сусідніх комірок замість усього світу.

---

## 8.2. Базове використання

```gdscript
var grid := UniformSpatialGrid.new()

# Один раз при складанні:
grid.configure(
    130.0,      # arena_radius: межа по площині XZ
    0.0,        # vertical_extent: 0 = плоский (2D) режим
    10.0,       # cell_size
    10000,      # entry_capacity: максимум записів за одну перебудову
)
```

Щокадру, **після** того як усі зрушилися:

```gdscript
grid.rebuild(entity_ids, points, entry_count)
```

Далі — запити:

```gdscript
# Найближчий у радіусі, або -1.
var nearest: int = grid.query_nearest(center, 12.0)

# Усі в радіусі. Повертає кількість; самі id — у query_buffer.
var found: int = grid.query_sphere(center, 10.0, 64)
for i in found:
    var entity: int = grid.query_buffer[i]
```

> **`query_buffer` перезаписується наступним запитом.** Читайте його одразу або
> копіюйте потрібне. Результат навмисно потрапляє в поле класу, а не в
> вихідний параметр: так власність і час життя результату очевидні, а повернення
> нового масиву не алокувало б пам'ять на кожен запит.

### Перебудова, а не переміщення

Сітка розрахована на сценарій «все рухається щокадру»: вона **не підтримує**
точкове переміщення об'єкта, а перебудовується цілком. Для симуляції, де майже
все зрушилося, це дешевше, ніж `n` окремих оновлень.

---

## 8.3. Плоский (2D) режим

```gdscript
grid.configure(130.0, 0.0, 10.0, 10000)     # vertical_extent = 0
```

Якщо ваша гра відбувається на площині — top-down, RTS, bullet hell, симуляція в
чашці Петрі — передайте `vertical_extent = 0.0`, і сітка згорнеться в один шар.

Координата Y тоді ігнорується при розкладанні по комірках (перевірки відстані
далі повністю тривимірні), а кількість комірок падає в стільки разів, скільки
вертикальних шарів було б інакше.

У замірах на тих самих даних: перебудова 10 000 записів **3.06 мс у 3D проти
2.21 мс у плоскому режимі** (10 125 комірок проти 2 025).

Перевірити режим: `grid.is_flat()`, `grid.get_dimensions()`.

---

## 8.4. Найважливіше: підбір `cell_size`

Вартість `rebuild()` — це **`O(записи + ЧИСЛО КОМІРОК)`**, а не тільки
`O(записи)`.

Причина всередині алгоритму: сітка побудована на **counting sort**, і його
другий прохід (префіксні суми) зобов'язаний пройти по **всіх** комірках,
включно з порожніми. Сітка з 10 000 комірок, у якій живе 30 об'єктів, майже весь
час витрачає на порожнечу.

Дві сили тягнуть у різні боки:

- **дрібні комірки** розоряють перебудову, але прискорюють запити — у кожній
  комірці менше кандидатів;
- **великі комірки** роблять перебудову майже безкоштовною, але запити
  деградують: доводиться перевіряти відстань до купи зайвих кандидатів.

Заміри на арені 130 × 24 (у дужках — `get_cell_count()`):

| `cell_size` | комірок | `rebuild` 32 записи | `rebuild` 10 000 | 512 × `query_nearest` |
|---|---|---|---|---|
| 3 | 69 696 | 2257 мкс | 4.7 мс | 4.9 мс |
| 6 | 10 125 | 338 мкс | 2.8 мс | 3.4 мс |
| 10 | 2 916 | 102 мкс | 2.6 мс | 3.4 мс |
| 16 | 972 | 39 мкс | 2.5 мс | 4.2 мс |
| 26 | 242 | 16 мкс | 2.5 мс | 6.2 мс |
| 40 | 128 | 12 мкс | 2.5 мс | 9.4 мс |
| 65 | 50 | 10 мкс | 2.5 мс | 18.3 мс |

### Правило великого пальця

Тримайте `get_cell_count()` **співмірним із очікуваною кількістю об'єктів**, а
сам `cell_size` — у 2–4 рази більшим за типовий радіус запиту.

Або просто спитайте бібліотеку:

```gdscript
var size: float = UniformSpatialGrid.suggest_cell_size(
    130.0,      # arena_radius
    0.0,        # vertical_extent (0 = плоский)
    10000,      # очікувана кількість об'єктів
    12.0,       # типовий радіус запиту
)
grid.configure(130.0, 0.0, size, 10000)
```

Формула бере «приблизно одна комірка на об'єкт» і піднімає результат до
щонайменше подвоєного радіуса запиту. Це стартова точка, а не закон — далі
профілюйте.

### Кілька сіток із різними `cell_size`

Це **рекомендований патерн**, а не хитрощі.

Якщо у сцені є і щільна маса дрібних об'єктів, і десяток великих рідкісних, одна
спільна сітка погана для обох. Заведіть дві:

```gdscript
# 10 000 юнітів, дрібні комірки: перебудова дорога, але запити швидкі
units_grid.configure(130.0, 0.0, 6.0, 10000)

# 30 снарядів, великі комірки: ітерувати 10 000 порожніх комірок заради
# тридцяти записів було б чистою втратою
missiles_grid.configure(130.0, 0.0, 40.0, 64)
```

Реальний вимір із гри, де ракети спершу ділили сітку з ворогами: перехід на
окрему сітку з `cell_size = 40` замість 6 дав **350 → 17 мкс**, тобто мінус 12%
кадру.

## 8.5. Позиції разом з ідентифікаторами

Типовий цикл «знайти сусідів і порахувати силу» після `query_sphere()` мусив би
для кожного знайденого id ще й дістати його позицію через власне сховище. Сітка
вже має ці позиції:

```gdscript
grid.store_query_points = true          # один раз

var found: int = grid.query_sphere(center, 10.0, 64)
for i in found:
    var entity: int = grid.query_buffer[i]
    var point: Vector3 = grid.query_point_buffer[i]     # без зайвого пошуку
    var push: Vector3 = (center - point).normalized()
```

Типово вимкнено, щоб ті, кому потрібні лише id, не платили за зайвий запис.

## 8.6. Власний обхід по комірках

Для нестандартних задач — «усі пари всередині комірки», нестандартна форма
області, k найближчих — сітка відкриває свої відсортовані масиви:

```gdscript
var cell: int = grid.get_cell_index(point)
var start: int = grid.get_cell_start(cell)
var end: int = grid.get_cell_end(cell)

for s in range(start, end):
    var entity: int = grid.sorted_entities[s]
    var position: Vector3 = grid.sorted_points[s]
```

`sorted_entities` і `sorted_points` — **тільки для читання**, за тією ж
домовленістю, що й публічні поля сховищ.

## 8.7. Геометричні припущення

- Світ центрований у нулі по осях **X і Z**: діапазон
  `[-arena_radius, +arena_radius]`.
- По **Y** відлік іде вгору від нуля: діапазон `[0, vertical_extent]`.
- Об'єкти **за цими межами не губляться** — вони затискаються у крайні комірки,
  тому запити біля межі арени лишаються коректними.
- `query_sphere()` при досягненні ліміту **припиняє пошук**, тому обрізаний
  результат зміщений до нижнього кута області пошуку, а не є випадковою вибіркою.

## 8.8. `AngleMath`

Маленький незалежний модуль для плавного довороту.

```gdscript
# Довернути current до desired, не більш ніж на max_step, найкоротшим шляхом.
yaw = AngleMath.approach(yaw, desired_yaw, turn_rate * delta)

# Абсолютна найкоротша кутова відстань — «наскільки далеко», без напрямку.
if AngleMath.shortest_delta(yaw, desired_yaw) < firing_tolerance:
    fire()
```

**Чому це не тривіально.** Наївне
`current += clamp(desired - current, -max_step, max_step)` ламається на переході
через ±π. Якщо `current = 3.1`, а `desired = -3.1`, різниця «в лоб» дорівнює
−6.2 рад, хоча найкоротший шлях між цими кутами — усього 0.08 рад **в інший бік**.
`wrapf(..., -PI, PI)` приводить різницю до найкоротшого еквівалента ще до
обмеження кроком.

---

## Головне з розділу

1. Сітка **перебудовується цілком** щокадру; точкового переміщення немає.
2. Вартість перебудови — `O(записи + КОМІРКИ)`, тому `cell_size` критичний.
3. **Плоский режим** (`vertical_extent = 0`) — безкоштовне прискорення для гри
   на площині.
4. `suggest_cell_size()` дає обґрунтовану стартову точку.
5. Різні за населенням набори об'єктів потребують **різних сіток** із різним
   `cell_size`.
6. `query_buffer` перезаписується наступним запитом.
7. `AngleMath.approach()` — коректний доворот через ±π.
