# 3. Світ, сутності, життєвий цикл

`EcsWorld` — це розподільник ідентифікаторів сутностей і реєстр сховищ. Він не
зберігає ігрових даних; він відповідає на питання «які сутності живі» і «які
сховища існують».

---

## 3.1. Створення світу

```gdscript
var world := EcsWorld.new(10000)   # ємність: 10 000 одночасно живих сутностей
```

Ємність задається один раз, і всі внутрішні буфери виділяються **одразу**. Світ
**не росте сам** — це свідоме рішення. Прихована алокація в гарячому циклі при
десятках тисяч сутностей дає фриз на слабкому пристрої, а фриз, який стається
раз на кілька хвилин у випадковий момент, майже неможливо відлагодити.

Якщо ємності може забракнути — читайте про явне зростання й автоматичну політику
в [розділі 7.3](07-chas-podii-yemnist.md#73-ємність-і-політика-зростання).

### Порядок складання світу

```gdscript
var world := EcsWorld.new(10000)

# 1. Спочатку ВСІ сховища.
world.register_store(positions, TYPE_POSITION)
world.register_store(velocities, TYPE_VELOCITY)
world.register_store(enemy_tag, TYPE_ENEMY)

# 2. Потім системи.
scheduler.add_system(...)
scheduler.setup_all(world, context)

# 3. І лише тепер — сутності.
var entity: int = world.create_entity()
```

Схема **блокується першим `create_entity()`**: після нього `register_store()`
поверне `false` і надрукує помилку. Це навмисно — сховище, зареєстроване пізніше,
не знало б про вже створені сутності, і його sparse-масив був би неузгоджений.

Ідентифікатор типу (`TYPE_POSITION` тощо) — будь-яке ціле на ваш розсуд, зазвичай
константи вашого власного переліку. Світ використовує його лише для
`get_store()` і діагностики; на швидкість він не впливає.

## 3.2. Сутність — це число

```gdscript
var entity: int = world.create_entity()
if entity < 0:
    return            # світ заповнений — перевіряти ОБОВ'ЯЗКОВО
```

`create_entity()` повертає **-1**, коли вільних ідентифікаторів більше немає. Це
не виняток і не помилка — це нормальний стан переповненого світу, і викликальний
код зобов'язаний його перевіряти.

Ідентифікатор — це щільний індекс у діапазоні `[0, capacity)`. Він напряму
адресує `sparse_index` кожного сховища, тому лишається найдешевшим представленням
у гарячому циклі: жодного декодування, жодної перевірки.

### Пакетне створення

Коли за кадр народжується багато сутностей — хвиля ворогів, вибух на частинки,
поділ клітин — платити накладні витрати на кожен виклик не варто:

```gdscript
var buffer := PackedInt32Array()
buffer.resize(256)                                  # один раз, наперед

var spawned: int = world.create_entities(64, buffer)
# spawned може бути меншим за 64, якщо світ майже повний
```

`buffer` заповнюється на місці (у Godot 4 `Packed*Array` передаються за
посиланням). Далі цей самий буфер віддається сховищам:

```gdscript
var first_slot: int = positions.count      # ЗНЯТИ ДО виклику
positions.attach_many(buffer, spawned)
for i in spawned:
    positions.x[first_slot + i] = 0.0
```

Нові компоненти займають слоти `[first_slot, first_slot + attached)` **у тому
самому порядку**, в якому сутності йшли у буфері.

## 3.3. Handle: посилання, що переживає кадри

Сирий ідентифікатор безпечний **тільки в межах структурної епохи** — тобто доки
не викликано `flush_destroy_queue()` або `reset()`. Після знищення той самий
номер може отримати інша сутність.

Тому для всього, що живе між кадрами — ціль турелі, власник ефекту, елемент UI,
відкладений колбек, зовнішня черга — існує **generational handle**:

```gdscript
var handle: int = world.make_handle(entity)

# ...багато кадрів потому:
var current: int = world.entity_from_handle(handle)
if current == EcsWorld.INVALID_ENTITY:
    return          # ціль загинула; handle протух
# тут current знову можна використовувати як звичайний id
```

Handle — це додатне 63-бітове число, у яке запаковано три речі:

```
біти  0..23  сирий id сутності   (до 16 777 216 слотів)
біти 24..47  покоління (generation)
біти 48..62  тег світу
```

**Покоління** — лічильник, що зростає щоразу, коли слот звільняється. Тому старий
handle на перевикористаний слот не збігається за поколінням і буде відхилений.
Це захист від класичної **ABA-проблеми**: «те саме число, але вже інша сутність».

**Тег світу** захищає від того, щоб handle одного світу випадково розв'язався в
іншому (актуально, якщо у вас кілька незалежних симуляцій).

### Правило вибору

| Ситуація | Що зберігати |
|---|---|
| Всередині одного кадру, всередині системи | сирий `int` |
| Ціль, власник, підписка, UI, tween, async | `handle` |
| Збереження на диск, мережа | **власний GUID**, не handle |

Handle **не є** стабільним ідентифікатором між запусками гри: він містить тег
процесу й покоління, які при новому запуску інші.

### Допоміжні методи

```gdscript
world.create_entity_handle()          # створити і одразу отримати handle
world.is_handle_alive(handle)         # без розв'язання в id
world.queue_destroy_handle(handle)    # безпечне знищення за handle
world.is_handle_pending_destroy(handle)
```

## 3.4. Знищення: найважливіше правило

Ще раз, бо це те місце, де ламаються всі ECS-новачки.

```gdscript
world.queue_destroy(entity)     # ТІЛЬКИ позначає
world.flush_destroy_queue()     # реально знищує
```

`queue_destroy()` **ідемпотентний**: якщо кілька систем у одному кадрі незалежно
вирішать убити ту саму сутність, у чергу вона потрапить один раз.

`flush_destroy_queue()` — це **structural sync point**. Він:

1. перевіряє покоління кожного запису черги;
2. від'єднує сутність від кожного зареєстрованого сховища;
3. виконує swap-remove і хуки очищення;
4. позначає сутність мертвою;
5. збільшує покоління;
6. і лише тоді повертає id у пул вільних.

### Де його викликати

Використовуйте готовий `EcsReaperSystem`, зареєстрований **останнім**:

```gdscript
scheduler.add_system(MovementSystem.new())
scheduler.add_system(CombatSystem.new())
scheduler.add_system(EcsReaperSystem.new(world))    # ← остання
```

Технічно flush можна ставити на кількох явних межах фаз. Але **ніколи** — усередині
системи, і **ніколи** не можна кешувати щільний слот через цю межу:

```gdscript
# НЕПРАВИЛЬНО
var slot: int = positions.index_of(entity)
world.flush_destroy_queue()          # тут swap-remove міг перемістити дані
positions.x[slot] = 0.0              # пишемо в чужий компонент
```

Handle лікує протухле **посилання на сутність**, але не протухлий **щільний
слот**. Слот треба брати заново після будь-якої структурної зміни.

### Пакетне позначення

```gdscript
world.queue_destroy_many(buffer, count)
```

## 3.5. Reset: перезапуск рівня без алокацій

```gdscript
world.reset()
```

Усі сутності «вмирають», усі сховища очищаються — **без жодної алокації**:
масиви просто перезаповнюються. Реєстрації сховищ зберігаються, повторно
викликати `register_store()` не треба й не можна.

`reset()` інвалідує всі активні handle: покоління кожної живої сутності
збільшується.

## 3.6. Діагностика

```gdscript
world.get_live_count()             # скільки сутностей живих
world.get_free_count()             # скільки id лишилося
world.get_retired_count()          # слоти з вичерпаним поколінням
world.get_pending_destroy_count()  # скільки чекає у черзі
world.get_load_factor()            # live / capacity, у [0, 1]
world.capacity
world.structural_version           # монотонний лічильник структурних змін
```

### Перевірка цілісності

```gdscript
if not world.validate_integrity():
    breakpoint
```

Повна перевірка розподільника, черги знищення й усіх sparse-множин: сходяться
чи ні лічильники, чи немає дублікатів у списку вільних, чи бієктивні
sparse↔dense відображення, чи не прикріплений компонент до мертвої сутності.

Перевірка **лінійна за ємністю** і створює тимчасові буфери. Це інструмент
розробки: викликайте його з тестів, з debug-панелі або у fuzz-циклі, але **не з
продакшн-кадру**.

`validate_integrity(false)` не друкує помилок, а лише повертає `bool` — зручно
для тестів.

---

## 3.7. Кілька світів

Нічого не заважає мати кілька незалежних `EcsWorld` — наприклад, по одному на
матч, на рівень або на паралельну симуляцію. Тег світу в handle гарантує, що
посилання одного світу не розв'яжеться в іншому.

Обмеження: тегів вистачає на 32 767 світів, створених за час життя процесу
(вони не перевикористовуються). Після вичерпання світи продовжують працювати з
сирими id, але handle-API повідомляє помилку. На практиці це недосяжна межа, якщо
ви не створюєте новий світ щокадру.

---

## Головне з розділу

1. Ємність фіксується при створенні; світ не росте сам.
2. Усі сховища реєструються **до** першої сутності.
3. `create_entity()` може повернути **-1** — перевіряйте завжди.
4. Сирий id — у межах кадру; **handle** — між кадрами; **власний GUID** — у файл.
5. `queue_destroy()` позначає, `flush_destroy_queue()` знищує — **рівно в одній
   точці кадру**, зазвичай через `EcsReaperSystem`.
6. Не кешуйте щільний слот через структурну зміну.
